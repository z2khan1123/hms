# Data model

## Principles

- **UUID v4 primary keys** everywhere. Never expose sequential integers; they leak
  volume and enable enumeration.
- **`tenantId` on every tenant-scoped table**, first column of most composite
  indexes, protected by RLS (see `architecture.md`).
- **Soft delete** (`deletedAt`) for clinical records — you keep history for audit
  and medico-legal reasons; hard delete is a separate, logged, privileged action.
- **Timestamps** `createdAt` / `updatedAt` on everything.
- **Money** as integer minor units (paisa) + ISO currency code. Never floats.
- **FHIR alignment**: entity and field names track the matching FHIR R4 resource
  so a FHIR facade is a mapping exercise, not a migration.

## MVP entities

| Table            | FHIR analogue         | Notes                                        |
| ---------------- | --------------------- | -------------------------------------------- |
| `Tenant`         | (platform)            | A hospital/customer. No RLS.                 |
| `User`           | Practitioner / (staff)| Login identity. Belongs to one tenant.       |
| `Role`           | —                     | Enum-like; maps to permissions in `@hms/shared`. |
| `Patient`        | Patient               | Demographics, contact, identifiers.          |
| `Practitioner`   | Practitioner          | A doctor/clinician who can be scheduled.     |
| `Schedule`       | Schedule              | A practitioner's bookable window.            |
| `Appointment`    | Appointment           | Booking linking patient + practitioner + slot.|
| `AuditEvent`     | AuditEvent            | Append-only. No RLS-bypass, no update/delete.|

### Patient — key fields

```
id            uuid pk
tenantId      uuid
mrn           text     -- Medical Record Number, unique per tenant
firstName     text
lastName      text
gender        enum(male, female, other, unknown)   -- FHIR administrative-gender
birthDate     date
phone         text     -- E.164, Pakistan +92...
email         text?
nationalId    text?    -- CNIC; store hashed + last4 if used for matching (see security.md)
address       jsonb?   -- { line1, line2, city, province, postalCode, country }
bloodType     text?
status        enum(active, inactive, deceased)
createdAt / updatedAt / deletedAt
```

Indexes: `(tenantId, mrn)` unique, `(tenantId, lastName, firstName)`,
`(tenantId, phone)`.

### Appointment — key fields

```
id             uuid pk
tenantId       uuid
patientId      uuid  -> Patient
practitionerId uuid  -> Practitioner
startsAt       timestamptz
endsAt         timestamptz
status         enum(booked, arrived, fulfilled, cancelled, noshow)   -- FHIR appointment-status subset
reason         text?
notes          text?
createdBy      uuid  -> User
createdAt / updatedAt
```

Indexes: `(tenantId, practitionerId, startsAt)`, `(tenantId, patientId, startsAt)`.
Overlap check is enforced in the service layer for the MVP; a Postgres exclusion
constraint (`tstzrange` + `btree_gist`) is the hardening step (see roadmap).

### AuditEvent — key fields

```
id          uuid pk
tenantId    uuid?         -- null for platform-level events
actorId     uuid?         -- User id, null for system
action      text          -- e.g. "patient.read", "appointment.create"
entityType  text
entityId    text?
method      text          -- HTTP method
path        text
ip          text?
userAgent   text?
outcome     enum(success, failure)
metadata    jsonb?        -- never store full PHI payloads here
createdAt    timestamptz
```

Append-only: no `UPDATE`/`DELETE` grant for the app role. Ships to a separate
log sink in production.

## ID / identifier strategy

- **MRN** is the human-facing patient identifier, unique per tenant, generated by
  the API (configurable prefix + zero-padded sequence per tenant).
- **CNIC (national ID)** is sensitive. For the MVP it is optional and, when
  provided, stored as a salted hash plus the last 4 digits for lookup/disambiguation
  — not in plaintext. Revisit if a verified-identity feature needs the full value
  (then it belongs in an encrypted column with restricted access).

## Migrations

Prisma Migrate. Migration files are committed under
`apps/api/prisma/migrations/`. RLS policies and the audit-table grants are added
as raw SQL in a dedicated migration (Prisma does not model RLS).
